# Structured editing and concurrent reconciliation

The structure actions operate on immutable document revisions. They neither publish content nor alter approvals. A successful edit creates an ordinary revision, preserving the current title, tags and language. Reads require collection read access; previews and writes require edit access. Existing application transactions roll back failed operations, including events and allocated identities.

`structure.get` takes `documentId` and optional `revisionId`. It returns contiguous block source spans, heading sections with parent identities, list task metadata, fenced blocks and inline link positions. Offsets are zero-based UTF-16 code units; lines are one-based. Section ranges include descendant headings and end before the next heading of equal or lower level. Repeated slug titles get deterministic occurrence suffixes. Block and section identities contain their source position and a content digest: clients must obtain fresh identities after editing.

The parser intentionally supports ATX headings, consecutive list-item runs, backtick/tilde fences, paragraphs, blank blocks and inline links with balanced destination parentheses. It preserves source exactly and ignores headings and links inside fences. It is not a Markdown renderer: setext headings, HTML blocks, reference-style links and full multiline list nesting are outside its grammar. It reports unclosed fences explicitly. Inline code spans and escaped link brackets are skipped.

`structure.preview` and `structure.apply` require `documentId`, `expectedRevisionId`, `expectedChecksum`, and one to 100 `operations`. All operation coordinates refer to the original revision. Supported kinds are `rename` with `title`, `replace` with a replacement section `body` (including descendants), `delete`, `insertAfter` with `body`, `moveAfter` with `destinationId`, and `shiftLevel` with `level`. Every operation has `sectionId`. Moves between ancestors and descendants are rejected. Level changes include descendants and must keep all levels between one and six. Overlapping operations and ambiguous coincident insertions are rejected atomically. Preview returns proposed body, checksum and edit spans without changing state. Apply rejects unchanged documents. Generated headings use the source newline convention; replacement text itself is preserved and newline-terminated for section separation.

`structure.diff` takes `documentId`, `fromRevisionId`, optional `toRevisionId` and optional `maximumCells`. Hunks use zero-based half-open base line indexes and retain original line endings. A deterministic longest-common-subsequence algorithm trims shared prefix/suffix and caps its table at the supplied cell budget (default one million, maximum two million). When the middle exceeds the budget, the result is a complete conservative replacement with `exact: false`; it is never truncated.

`structure.merge.open` takes the document identity guards, `baseRevisionId`, and proposed incoming `body`. The base must be an ancestor of the current revision. It computes both changes against that base. Disjoint changes merge; identical overlapping results coalesce; competing replacements become explicit conflict records containing base/current/incoming fragments. Insertions sharing a boundary with another change conservatively conflict. Budget exhaustion may produce larger conflicts, never silent loss. The session stores the full immutable plan, version one, owner and target revision/checksum. This snapshot makes later conflict inspection independent of retained historical source.

`structure.merge.get` takes `id`. `structure.merge.resolve` takes `id`, `expectedVersion`, `conflictId` and `choice` (`base`, `current`, `incoming`, or `custom` with `body`). It replaces that conflict's resolution and increments the session version. Only the originating editor or an administrator may mutate the session. `structure.merge.commit` takes `id` and `expectedVersion`, requires every conflict resolved, checks the captured document identity, creates a normal revision and closes the session atomically. A stale session is never implicitly rebased. `structure.merge.abandon` closes an open session without editing a document. Closed sessions remain readable and reject further mutation.

The subsystem uses one added state table, `structureMerges`; the application's transaction snapshots and response cloning cover it automatically. No package dependency, background process or alternate revision store is introduced.

## Discussion anchors and review continuity

Comments remain physical-line observations of immutable revisions. Anchor migration does not move an existing comment, resolve it, change its review, or retarget an approval. Instead, immutable `structureAnchors` capture source evidence and `structureFollowups` link explicitly created new comments to that evidence.

`structure.anchors.capture` requires `documentId` and `expectedChecksum`. Supply `commentId` to capture the original comment's revision and line; optionally extend the quotation through `endLine`. A `reviewId` without a comment captures a line range of that review's revision. Otherwise use `revisionId` (default current), `startLine`, and optional `endLine`. Conflicting explicit revision/review/line identities are rejected. Optional `expectedQuote` verifies what the caller saw. Captures retain source revision/checksum, a quote and quote digest, two surrounding lines in each direction, containing section/block facts, and an original comment snapshot. Quoted ranges are bounded to 200 lines and 20,000 UTF-16 code units. `structure.anchors.get` returns a capture by `id` with current collection authorization.

`structure.compare` compares `fromRevisionId` with optional `toRevisionId` for a document. Its structural matches first require unique complete subtree checksums on both sides, then unique heading ancestry paths for edited candidates. Duplicate headings never collapse to a slug identity. Path-based candidates are expressly nonexact; deleted and ambiguous entries remain visible. The response also includes bounded source-line differences and unmatched target sections.

`structure.anchors.preview` takes `documentId` and unique `anchorIds` (one to 100). The optional `target` is `{kind: 'revision', revisionId}`, `{kind: 'sections', operations}`, or `{kind: 'merge', id, expectedVersion}`. Revision defaults to current. Proposed section/merge targets require edit permission plus `expectedRevisionId` and `expectedChecksum`; merge proposals must be open, current, and fully resolved. Proposal previews carry `committable: false` and no revision identity. They are evidence for the prospective edit, never permission to post against nonexistent content.

Each mapping reports `unchanged`, `relocated`, `edited`, `deleted`, or `ambiguous`, an exactness flag and a reason. Exact unchanged/relocated mapping requires a complete line-aligned quote, matching block kind, and uniqueness in both source and destination; repeated quotations may map only through uniquely preserved surrounding context. Identical full document bodies also preserve empty-line anchors. Changed empty anchors, duplicate evidence, fence-context changes and boundaries crossing replacement regions refuse exactness. A precise line replacement can suggest an edited range, but cannot claim the old observation is true of that range. Diff-budget exhaustion never supplies an exact fallback. Offsets use UTF-16 and ranges preserve CRLF, Unicode and original list text. The preview includes status counts and per-anchor diagnostics; up to twenty ambiguous candidates are exposed with their full count.

`structure.anchors.followup` takes the current `documentId`, `expectedRevisionId`, `expectedChecksum`, and an `entries` batch. Each entry has `anchorId`, new comment `body`, and an optional target `reviewId`. Exact mappings may supply no selection. Otherwise an explicit `selection: {startLine, endLine?, quote}` and `acknowledgedStatus` are required. The selected quote is verified against the current revision, so an edited/deleted/ambiguous result is never silently retargeted. Explicit selections are also allowed for exact mappings when the caller deliberately chooses a different context. An explicitly selected empty final line is valid under the existing comment API.

All batch entries are authorized and validated before any comments are created; the existing transaction also rolls back counters and events if any downstream creation fails. Duplicate anchor entries are rejected. A capture may have one follow-up per target revision and target review (including the no-review case). A selected target review must be open and pinned to the current revision. The follow-up record retains original comment/review/revision identities, target quote/checksum, selection mode, mapping status and new comment identity. `structure.anchors.followups` lists these provenance links by `anchorId`. New review comments participate in ordinary unresolved-comment checks; prior reviews and approvals retain their original meaning.

Anchor reading and follow-up creation require current collection read access, matching existing comment permissions. Proposed edit previews require edit access. Historical source revisions must still exist to validate a mapping; retention that removes one produces an explicit lookup failure, even though its captured quote remains available through anchor inspection. No fuzzy quotation score, line-number proximity or duplicate-heading occurrence is accepted as exact identity.
